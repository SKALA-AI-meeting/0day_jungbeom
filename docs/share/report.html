1.1 핵심 요약

60분 토론 한 번으로 인성 5요소의 행동 근거를 남긴다.

지원자가 AI 동료 3명과 키워드 · 문제 상황 · 해결책을 정하고 기획안을 내면, 평가 에이전트가 근거를 들어 수준을 제안하고 담당자가 최종 평가합니다.

표 1-1핵심 설계 결정

결정내용
결정은 코드, 말투는 LLM입장 · 합의 · 카드 시각 · 시간 초과는 규칙이 정하고, LLM은 화자 보조와 발언 문장만 만든다
세션별 메일박스자극 4종을 Task 하나가 차례로 처리한다. 새 지원자 메시지가 오면 남은 화자는 버린다
시간과 쓰기의 주인은 api시간 초과 채우기와 업무 데이터 쓰기는 api만 한다(체크포인트 · 색인은 예외). MCP와 워커는 /internal을 부른다
평가 정보 차단페르소나는 assessment-mcp에 닿지 않는다(허용 목록 + 토큰)

핵심 메시지

AI 동료는 평가 기준을 모른다토론에 참여하는 페르소나는 척도와 관찰 기록에 접근할 수 없습니다.
판단은 근거로, 확정은 사람이근거 없는 수준은 내지 않고, 담당자가 차원 단위로 조정합니다. 총점은 없습니다.

1.2 문제 정의와 서비스 구성

말로 묻는 검사 대신 토론 속 행동을 근거로 쓴다.

기업은 인성과 협업 태도를 중요하게 보지만 측정은 자기 보고와 짧은 면접에 기댑니다. Day Zero는 그 태도가 드러나는 상황을 토론으로 만들고 발언을 근거로 남깁니다.

표 1-2문제와 근거

문제근거
원하는 것과 재는 것이 다르다면접 유형은 질의응답이 94.1%, 실무 수행은 10.7%
자기 보고는 꾸밀 수 있다거짓말이 가장 잘 드러나는 전형으로 실무면접 65.5%, 인적성 검사 2.4%
잘못된 채용은 비싸다인사담당자 60.9%가 최근 1년 안에 신입 조기 퇴사를 경험
지원자는 이유를 모른다취업준비생 51.5%가 최종 면접 불합격 통보조차 받지 못함

문제 상황18분두 동료가 지원자 안과 다른 안을 지지하고 고집형 동료가 강하게 밈수용 · 경청
해결책18분소극형 동료가 말을 거두고, 비판형 동료가 지원자 안의 약점을 자료로 짚음배려 · 설득
기획안14분지원자가 6칸 템플릿을 혼자 써서 제출. 아이디어 기여 칸을 실제 최초 제안자와 대조정직
기업이 받는 것

지원자가 받는 것

말이 아닌 행동으로 보여 줄 기회와 디브리핑. 어떤 장면이 설계되어 있었는지 설명하고 이의 제기 경로를 줍니다.

3.1 에이전트 구성

참여자로 보이는 AI는 셋, 뒤에서 일하는 에이전트는 넷이다.

세션 중에는 api 안에서 의도 분류 · 토론 그래프 · 어시스턴트가 돌고, 세션이 끝나면 report-worker의 평가 에이전트가 돕니다.

표 3-1에이전트별 역할

에이전트하는 일도구
턴 매니저자극마다 화자 0~2명을 규칙으로 정하고, 결과가 0명인 메시지에만 LLM을 씀결정적 노드가 debate-mcp 전부 · record_observation
페르소나 × 3성향 · 고정 입장 · 자리 기억으로 1~3문장 발언get_transcript · get_draft · rag 2, 응답당 3회. DebateState는 컨텍스트로
의도 분류지원자 메시지를 저장된 단계(messages.phase) 기준으로 제안 · 동의 · 반대 · 질문 · 기타와 대상 안으로 분류없음, 10초 넘으면 기타
어시스턴트지원자 요청에 자료를 스스로 골라 인용과 함께 답함rag 2, 최대 3회
평가 에이전트요소마다 1회 호출로 차원별 수준 · 근거 · 확신도 판단없음(워커가 입력 주입)

표 3-2세션 페르소나

자리이름 · 유형토론에서 하는 일
p1강한결 · 고집형자기 안을 반복해 밀고 반대에 바로 재반박. 확정 전에는 입장을 바꾸지 않음. 서지안이 못 맡는 설득 카드를 대신 맡음

3.2 토론 턴 흐름

메시지 한 번은 분류, 화자 선택, 발언, 검사를 거쳐 게시된다.

토큰 스트리밍 없이 guard를 통과한 완성 문장만 게시합니다. 결과는 WebSocket으로, 저장은 MCP를 거쳐 api가 합니다.

표 3-3토론 턴 규칙

규칙처리
끼어들기지원자 메시지를 저장하면 generation이 +1 됩니다. 그래프는 게시 직전에 값이 바뀐 것을 보고 남은 화자를 버립니다
입력 중 표시클라이언트는 5초마다 typing을 갱신하고 서버는 6초 동안 갱신이 없으면 만료합니다
검사guard는 점수 · 판정 · 결론 대리 · 미래 카드 암시를 막고, stance_check는 계획 밖 입장을 막습니다. 각각 재생성 1회 뒤 고정 문구
실패발언 실패는 그 발언만 생략(연속 3회면 세션 실패), turn LLM 실패는 규칙 결과만, MCP 장애는 1회 재시도

3.3 단계 전환과 칸 확정

단계 시간과 칸 확정은 규칙이 정하고 LLM은 문장만 만든다.

칸 상태는 empty와 confirmed 두 개이고, 확정 경로에는 LLM이 없습니다. 칸마다 합의 · 시간 초과와 채운 사람을 남깁니다.

표 3-4단계 중 사건과 처리

사건감지처리
지원자 확정[이걸로 정하기]확인 창 하나 뒤 칸 확정, 다음 단계로. 키워드는 후보 버튼
AI 합의 채우기턴 매니저 fill지원자 포함 3/4 지지면 fill_slot 한 번으로 api가 한 트랜잭션에서 재검사 · 칸 확정 · "그럼 X로 정리할게요." 저장 · generation +1. 409면 저장 없음
단계 마감스케줄러 · 칸이 비어 있음api가 한 트랜잭션으로 안을 고르고 우선순위 자리 이름으로 고정 문장 게시
침묵 초대스케줄러 · 지원자 침묵서지안이 "OO님은 어떻게 생각하세요?" 단계당 1회
카드 시각단계 시작 + offset담당 화자가 고정 내용을 말하고 메시지의 card_ids로 카드마다 전달 자리를 기록. 담당 전원이 말할 때까지 card_due를 다시 넣음. 발언 없는 honesty_credit만 기획안 단계 시작 때 cards 노드가 기록
세션 만료스케줄러 · 종료 시각현재 기획안 초안을 자동 제출하고 세션 종료
시간 규칙

단계 마감 시각은 고정이라 일찍 확정하면 남은 시간이 다음 단계로 넘어갑니다. 15분 데모는 같은 비율이고 카드 시각은 최소 20초이며, 시간 로직은 가짜 시계 단위 테스트로 검증합니다.

4. MCP 설계와 접근 경계

MCP 세 개가 손 · 눈 · 기록자를 나누고, 페르소나는 평가 기록에 닿지 않는다.

5. 평가 설계(BARS)

평가 에이전트는 근거가 있을 때만 수준을 내고, 최종 평가는 담당자가 한다.

세션이 끝나면 큐 작업으로 리포트 그래프가 돕니다. 요소마다 따로 호출해 다른 요소 결과를 보지 않게 하고, 초안 뒤에는 담당자 검토를 기다립니다.

표 5-1요소별 하위 차원

요소차원하위 차원
설득/논리력4근거 제시 · 반론 대응 · 경쟁 안 비교 · 논의 수렴
경청/존중4응답성 · 이해 확인 · 타당성 인정 · 존중하는 반대
배려/포용4초대하기 · 들은 의견 이어받기 · 말하기 편한 분위기 · 결정 전 목소리 확인
수용/유연성4다른 안 재검토 · 결정 절차 존중 · 결과 승복 · 다음 단계 기여
정직/공정3기여 기록의 정확성 · 토론 중 출처 존중 · 결정 과정의 사실 표현
차원마다 내는 것

수준 1~5 또는 기록 없음과 사유, 근거 참조(메시지 · 칸 · 기획안 필드), 판단 이유 1~3문장. 확신도는 기록이 있을 때 high · medium · low, 기록 없음이면 null입니다.

총점 없음 · 사람 확인

요소 수준은 차원 평균의 반올림입니다. 담당자는 차원 단위로 조정하고 메모를 남기며, 합격 · 순위는 만들지 않습니다.
