③흐름 · 토론 · 단계 전환 · 평가 파이프라인

Sequence · Event-Driven. 자극은 세션 메일박스를 거쳐 토론 그래프가 하나씩 처리하고 결과는 WebSocket으로, 평가는 세션 종료 뒤 큐로 갑니다.

③-1 토론 한 턴 · 지원자 메시지 → AI 동료 발언

  • 끼어들기 · 지원자 메시지를 저장하면 generation이 +1 됩니다. 실행 중인 그래프는 게시 직전에 generation이 바뀐 것을 보고 남은 화자를 버리고, 메일박스는 새 메시지 자극을 이어서 처리합니다. 낡은 자극이라도 의도 분류와 지지 반영은 반드시 하고, 건너뛰는 것은 턴 선택과 발언 생성뿐입니다. 단계 전환도 generation을 올립니다.
  • 입력 중 표시 · 클라이언트는 입력 중 5초마다 typing을 갱신하고 서버는 6초 동안 갱신이 없으면 만료합니다. 토큰 스트리밍 없이 guard를 통과한 완성 문장만 게시합니다.
  • 실패 · 페르소나 발언이 재시도 뒤에도 실패하면 그 발언만 생략(연속 3회면 세션 failed), turn LLM 실패는 규칙 결과만, MCP upstream 실패는 1회 재시도합니다.

③-2 단계 전환과 타이머

표 3-2. 단계 중 사건과 처리

사건감지처리
단계 시작advance_phase가 phase_started를 메일박스에 넣음고정 입장 자리 1~2명이 첫 발언(소극형 제외, 문제 상황은 카드 전이라 입장 없이 일반 발언, 기획안 단계는 0명). 키워드 확정이면 그 자료를 열고 materials.opened. 기획안 단계 시작이면 cards 노드가 honesty_credit을 기록(발언 없는 유일한 카드)
AI 합의 채우기턴 매니저 fill지원자 포함 3/4면(apply 뒤 재판정 포함) fill 전용 분기가 respond · apply 없이 fill_slot{option_id, seat, content} 한 번. api가 한 트랜잭션에서 재검사 → 칸 confirmed → 지지자 중 서지안 > 윤하람 > 강한결 첫 자리 이름의 "그럼 X로 정리할게요." 저장 → generation +1. WS는 message.new → slot.confirmed → phase.changed → timer 순서. 409면 아무것도 저장하지 않음
단계 마감스케줄러 · 마감 시각, 칸 emptyapi가 한 트랜잭션으로 안 선택 → 우선순위 자리 이름으로 "시간이 다 돼서 대화에서 가장 많이 모인 의견으로 X로 할게요." 저장 → 칸 confirmed(timeout) → 다음 단계
침묵 초대스케줄러 · 지원자 침묵 조건idle → 서지안이 "OO님은 어떻게 생각하세요?"(is_invite=true). 단계당 1회, invite_delivered가 될 때까지 다시 넣음. 뒤이은 지원자 첫 발언은 origin=invited
카드 예정 시각스케줄러 · 단계 시작 + offset_mincard_due{card_id} → 담당 화자가 고정 내용을 말함. 메시지의 card_ids 카드마다 delivered_seats에 자리 추가(발언 하나가 두 카드를 겸할 수 있음). 담당 전원이 게시하기 전이면 남은 화자는 다음 run에서 이어서, 스케줄러도 새 run_id로 card_due를 다시 넣음(최초 포함 카드당 최대 3회, 30초 간격). flexibility_majority는 이때 기준안을 잠금
마감 임박 · 세션 만료스케줄러마감 L/30 전 시스템 안내 1건. ends_at이면 현재 기획안 초안을 자동 제출(auto_submitted=true) → session.ended{timeout}
지원자 제출웹 [제출]저장 완료 → 최신 초안의 빈 칸 검사 → 빈 칸이 있으면 빈칸 경고 → 제출 확인 → proposal/submit{blank_warning_shown}. api가 제출 때 빈 칸 목록과 경고 확인 여부를 저장해 관리자 리포트의 사실 지표와 기록에 보여 줌(평가는 맥락 참고만)

③-3 평가 파이프라인 · report-worker

  • 사람 확인 · interrupt에서 체크포인트를 먼저 저장한 뒤 draft 저장 → report_ready → ack 순서라, ack 뒤 승인이 와도 재개할 대상이 있습니다. 담당자가 차원 단위 조정 · 메모를 남겨 검토 완료하면 report.approve{session_id, eval_round}가 thread report:{session_id}:{eval_round}를 재개합니다. 평가를 다시 돌리면 새 회차 thread에서 collect부터 시작합니다. final은 draft content를 그대로 저장하고(해시 동일), 조정(rubric_adjustments)은 조회할 때 병합합니다.
  • 리포트 내용 · elements · dimensions(근거 원문 · 오피스 시각 · 앞뒤 맥락) · facts · contribution_check(안별 실제 최초 제안자 / 기획안에 적힌 기여자) · seats · slots(칸 결과 outcome 포함) · debrief. 1회 재요청 뒤에도 유효한 출력이 없는 차원(evaluate_failed)만 "판단 보류 · 근거 부족 — 원문 기록 확인 권장"으로 표시합니다. 활동 없음 · 해당 없음 · 이벤트 미발생 · 자동 제출로 기여 칸 미작성은 별도의 기록 없음 사유와 문구입니다. 총점 · 합격 · 순위는 없습니다.
  • 실패 · 노드 예외는 attempt+1 재발행(백오프 5 · 15 · 45초), 최초 포함 3회면 report.dlq → report_failed.

④MCP 역할과 접근 경계

세 서버 모두 FastMCP · Streamable HTTP(도구는 async def)이고 api /internal을 불러 저장합니다(rag-mcp의 청크 검색 · 재색인만 직접). 상태 판단은 api가 하고 MCP는 전달만 합니다. 오류는 {ok: false, error: {code, message, retryable}}입니다.
