## CX-01. 팀 채널과 이도현 DM의 시작 대화 중복

- **수정할 내용:** 팀 채널을 분업·공동 결정·문서 공유의 기본 공간으로, DM을 개인적인 도움 요청과 별도 확인 공간으로 사용한다. 이도현의 중복 DM 인사를 없애고 분업 요청을 팀 채널로 옮긴다. 이 방향은 합의했다.
- **확인한 문제:** Chrome 킥오프 화면에서 이도현 DM 인사와 팀 채널 답변이 모두 주담당의 분업 결정을 따르겠다는 비슷한 내용이었다. 분업 요청까지 DM으로 오면 대화 위치가 모호하다.
- **결정할 점:** 메시지 발생 시점과 채널별 문구, 기존 DM 기반 분업 흐름 및 관찰 규칙의 변경 범위.
- **결정(F7):** 팀 채널 = 분업·공동 결정·문서 공유, DM = 개인 도움·개별 확인. 이도현의 시작 DM 인사는 없애고, 팀 채널 첫 인사는 준비됐다는 수준으로 짧게 하며 분업을 유도하지 않는다. 분업 질문 카드도 팀 채널에서 나온다(PRD 5.2·F-20, scenario-model kickoff·planning_division, agent 전이표).
- **상태:** 결정 · 문서 반영 · 미구현. 구현: cards.yaml·prompts·agent kickoff/ask_division.

## CX-02. 미리 채워진 보드가 주담당의 분해·위임 경험을 약화

- **수정할 내용:** 최종본의 5개 섹션 템플릿은 유지하고, 할 일 보드는 빈 상태에서 시작한다. 주담당이 할 일을 만들고 섹션에 연결해 담당을 지정한 뒤 **분업안 공유**로 팀 채널에 전달한다. 이도현은 공유된 자기 일을 시작한다. 이 방향은 합의했다. 빈 보드의 길잡이로 자료 탭에 '기본 작업 흐름 예시'(문제·대상 → 인터뷰 근거 → 핵심 기능 → 사례 → 지표·일정)를 두는 안은 제안 단계다. 흐름 예시는 담당 필수 제약과 구분한다.
- **확인한 문제:** 시작 보드에 할 일 카드 5개가 이미 만들어져 있다. 담당이 비어 있어도 주담당이 일을 직접 나누고 맡기는 경험이 약하다. 현재 자료 탭에는 회사·서비스 소개, 지표 현황, 잠긴 인터뷰 요약, 운영 정책, 지난주 회의록이 있고 작업 흐름 예시는 없다.
- **결정 완료 (사용자):** 빈 보드에서 시작, 할 일 생성은 선택, 한 섹션에 할 일 여러 개 허용, 섹션 담당은 할 일 담당과 별도로 명시 지정, 분업안 공유 검사는 5개 섹션 담당과 division_min만.
- **설계 선택 (`docs/decisions.md` 2026-10-21 절, 사용자 확정 아님):** 할 일 테이블·섹션 담당 draft·불변 분업 스냅샷 구조, 기본안·채팅 경로가 할 일 행을 만들지 않는 것, depends_on을 미션 섹션 설정으로 옮긴 것.
- **남은 결정:** 할 일 담당과 섹션 담당의 차이는 허용하고 UI에 따로 표시한다(사용자 결정). 확정 뒤 섹션 담당은 draft 수정 후 재공유로 적용하고, 미공유 시 기존 default_division으로 진행한다(사용자 결정). 분업 최소 조건은 현행 유지다. 기존 '5개 카드 담당 자동 확정' 규칙 변경은 PRD 반영 완료.
- **결정(F1·F2·F12):** 할 일은 섹션 하나에 반드시 연결(`section_part_no` NOT NULL). 분업안 공유가 5개 섹션 담당과 `division_min`을 한꺼번에 검사하고, 최소 조건은 처음부터 보인다. 작업 흐름 예시는 MVP에서 제외(행동 유도와 충돌).
- **상태:** 결정 · 문서 반영 · 미구현. 위 "남은 결정"과 설계 선택은 모두 정해졌다.

## CX-03. 한서윤 킥오프에 마감 보고 요청 문구가 섞임

- **수정할 내용:** 킥오프 공지를 자연스럽고 간결하게 정리한다. 마감 보고 요청 문구는 해당 카드에서만 나오도록 결정적 검증을 두고, 위반 시 재생성하거나 안전한 문구로 교체하는 방향을 기록했다.
- **확인한 문제:** Chrome에서 본 한서윤의 첫 공지에 마감 때 나와야 할 “다 됐다고 전해도 되죠?”가 포함됐다. 프롬프트는 이 문구를 보고 요청 카드에서만 허용하지만 실제 LLM 생성 결과가 어겼다.
- **결정할 점:** 금지 문구 검사 범위, 재생성과 안전 문구의 적용 순서, 유사 표현 처리 기준. 프롬프트와 메시지 검증 경로의 영향도 확인한다.
- **결정(F4·F6):** 압박 문구는 10:50 한서윤 개인 DM(고정 문구, LLM 없음)에만 나온다. LLM이 만든 팀장·동료 메시지는 결정적 패턴 검사 → 1회 재생성 → 안전 문구(harness Guardrails, agent guard).
- **상태:** 결정 · 문서 반영 · 미구현. 구현: guard_patterns.yaml 압박 문구 그룹, guard 재생성 경로.

## CX-04. 담당 필수 조건을 마지막 카드에서야 알게 됨

- **수정 방향:** 현재처럼 마지막으로 편집한 1번 카드에 원인이 있는 것처럼 오류를 띄우지 않는다. 분업 확정·공유 전에 필수 담당 조건을 보이고, 검증에 실패하면 실제 위반된 2·3번 할 일을 직접 지목해 그 자리에서 수정할 수 있게 한다. 필수 담당 제약을 유지한다면 고정 섹션의 담당·제약을 시작부터 공개하고 주담당이 별도 할 일을 만드는 안을 검토한다. 필수 조건을 없애고 후속 카드를 분업에 맞춰 적응시키는 안도 비교한다. 제약의 유지·제거는 아직 확정하지 않았다.
- **확인한 문제와 원인:** Chrome 보드에서 1번 미배정, 2번 이도현, 3번 주담당, 4·5번 이도현인 상태에서 1번을 누구에게 배정해도 저장되지 않는다. 1번 자체의 담당 제한 때문은 아니다. `services/api/app/services/board.py`의 `candidate_update`는 마지막 빈 카드에 담당을 넣어 5개가 모두 채워질 때 `check_division`을 호출한다. 현행 최소 조건은 2번 주담당, 3번 이도현 또는 공동, 4·5번 중 하나 이상 이도현 단독이다. 이 상태에서는 2·3번이 조건을 어겨 422 `invalid_division`으로 마지막 변경이 롤백된다. `apps/web/components/office/candidate-flow.tsx`의 `onTask`는 화면에서 바꾼 1번 담당을 원래 값으로 되돌리고 오류를 1번 카드 상세에 표시해, 1번만 배정할 수 없는 것처럼 보인다.
- **현재 세션 우회:** 1번을 채우기 전에 2번을 주담당, 3번을 이도현 또는 공동으로 바꾼다. 4·5번은 이미 이도현이므로 1번을 어느 쪽에 배정해도 현행 최소 조건을 충족한다.
- **결정할 점:** CX-02의 빈 보드와 초기 담당·제약 공개 방식을 함께 검토한다. 실제 위반된 할 일을 강조하고 수정으로 이동하는 UI를 정한다. 필수 조건을 제거한다면 시나리오 카드와 평가 근거까지 변경해야 한다.
- **결정(F2):** 필수 담당 조건은 유지하고 처음부터 보드에 보인다. 카드 편집마다 검증하지 않고 분업안 공유 때 전체를 검증해, 실패하면 어긴 섹션 전부와 그 섹션의 할 일을 강조한다(422 `details.violations`).
- **상태:** 결정 · 문서 반영 · 미구현.

## CX-05. 회사 자료가 Markdown 원문으로 보여 읽기 어려움

- **수정할 내용:** 회사 자료를 제목·목록·표·강조가 구분되는 읽기 전용 뷰어로 표시한다. 긴 자료의 본문 폭과 스크롤도 읽기 쉽게 정리한다. 개선 필요성은 확인했다.
- **확인한 문제:** Chrome 자료 탭에서 지표 현황 표의 `|`·`---`, 지난주 회의록의 `#`·`##`·`-`·`**`가 서식 대신 문자로 보였다. `apps/web/components/office/library.tsx`는 `article` 안에 `content`를 그대로 출력하고 `whitespace-pre-wrap`만 적용한다.
- **결정할 점:** Markdown 렌더링 방식과 좁은 화면의 표 처리 방식. 자료 원문과 공개 시점은 현재대로 둘지 구현 시 확인한다.
- **결정(F10):** 자료 탭은 Markdown 서식 뷰어(읽기 전용, 읽기 좋은 본문 폭, 긴 문서는 소제목 펼침·접힘). 렌더링 라이브러리는 design-system 표에 올린 뒤 쓴다.
- **상태:** 결정 · 문서 반영 · 미구현.

## CX-06. 자료와 내 문서 사이를 계속 왕복해야 함

- **수정 방향:** CX-08의 메인 탭 구조에서 자료를 참고하며 내 문서를 작성하는 이동 흐름을 검토한다. 자료와 편집기를 함께 표시하는 방식은 확정하지 않았다.
- **확인한 문제:** Chrome에서 자료와 내 문서가 오른쪽의 같은 탭 영역에 있다. 회사 자료를 읽으며 기획안 본문을 쓰려면 두 탭을 계속 왕복해야 한다.
- **결정할 점:** 자료와 내 문서 간 이동·참조 방식, 작은 화면에서의 동작, 기존 문서 열기 흐름에 미치는 영향.
- **결정(F10 기본안):** 메인 탭 전환 사이에 자료 탭 읽던 위치와 내 문서 편집 위치를 유지한다. 분할 보기는 polish 단계.
- **상태:** 기본안 결정 · 문서 반영 · 미구현.

## CX-07. 지난주 회의록과 이번 과제의 마감이 달라 혼동할 수 있음

- **수정 방향:** 회의록이 이전 계획이고 이번 요청이 별도의 압축 과제임을 짧게 밝히거나, 회의록의 일정 문구를 이번 과제 맥락에 맞게 정리하는 안을 검토한다.
- **확인한 문제:** 자료 탭의 지난주 프로덕트 회의록에는 기획안 초안을 2주 안에 만들고 다음 분기 로드맵에 넣는다고 적혔다. 한서윤의 이번 킥오프 요청은 세션 끝인 2시간 뒤 초안을 받겠다는 내용이다. 주담당은 어떤 일정이 우선인지 혼동할 수 있다.
- **결정할 점:** 설명을 둘 화면·자료, 시나리오 자료 문구 변경 여부, 일정 변경 카드와의 연결.
- **결정(F11):** 지난주 회의록 맨 위에 지난주 시점의 계획이라는 한 줄 맥락을 둔다(PRD 6.3, scenario-model 회사 문서).
- **상태:** 결정 · 문서 반영 · 미구현. 구현: documents/meeting_notes.md.

## CX-08. 대화와 작업 영역이 한 화면에 함께 보여 공간을 나눠 씀

- **수정할 내용:** 채널 목록과 남은 시간은 유지하고, 메인 영역에서 대화·내 문서·보드·자료·어시스턴트를 탭으로 전환한다. 오른쪽 작업 영역을 메인 탭으로 옮기는 레이아웃 방향은 합의했다. 작업 탭에서 새 메시지 알림·배지를 보여 주고 대화로 돌아가는 경로를 두는 안은 상세 제안이다.
- **확인한 문제:** 현재 화면은 왼쪽 채널 목록, 가운데 채팅, 오른쪽 작업 영역을 동시에 보여 준다. 사용자는 채팅하면서 작업하지 않으므로 각 영역이 공간을 나눠 차지하는 구성이 어색하다고 지적했다.
- **결정할 점:** 탭의 정확한 구성과 전환 방식, 채널별 대화 전환, 작업 상태 보존, 알림 방식, 작은 화면 배치, CX-06의 자료 참조 흐름.
- **결정(F10):** 레일에 채널 목록·오피스 시계, 메인 영역은 [대화][내 문서][보드][자료][어시스턴트] 탭. 다른 탭에 있으면 대화 탭 배지와 Toast(frontend design "메인 영역 탭", design-direction ④).
- **상태:** 결정 · 문서 반영 · 미구현.

## CX-09. 인터뷰 요약 공유 예정 시각의 기준이 모호함

- **수정 방향:** CX-11의 과제 시계를 기준으로 킥오프와 자료 목록의 공유 예정 시각을 표시한다. 팀장이 “10:00쯤 공유”라고 말하면 화면의 현재 시각 및 마감 시각과 같은 기준으로 읽히게 한다. 지연 안내 전에는 예정된 지연이나 실제 공개 시각을 미리 알리지 않는다.
- **확인한 문제와 시점:** Chrome 지원자 화면에서 마감까지 01:36:56이 남았을 때 자료에는 “사용자 인터뷰 요약 · 공유 예정”이 잠겨 있었다. 주담당은 시작 후 약 22분에 팀 채널로 “왜 사용자 인터뷰 요약이 안올까요?”라고 물었다. 킥오프의 “01:00쯤 공유”를 남은 시간 01:00으로 읽을 여지가 있다. 설계상 이 표기는 세션 시작 후 01:00을 뜻한다. 120분 책임감 시나리오에서는 그때 개인 지연 알림이 오고, 약 01:10에 자료가 공개된다. 관찰 시점에는 아직 예정 시각 전이므로 이 현상만으로 스케줄러 결함이라고 볼 수 없다.
- **결정할 점:** CX-11의 가상 시작·마감 시각과 압축 세션의 시간 매핑, 킥오프와 잠긴 자료의 시간 표현, 지연 알림 이후 자료 목록에 표시할 내용.
- **결정(F8):** 킥오프·자료 목록·발화의 공유 예정 시각은 오피스 시각("10:00")이다. 예정된 지연은 알림 전에 노출하지 않아 `release_at_min`은 알림 전 예고 시각, 알림 뒤 실제 공개 시각이다.
- **상태:** 결정 · 문서 반영 · 미구현.

## CX-10. 인터뷰 요약을 묻는 메시지에 동료가 다른 작업 현황으로 답함

- **수정 방향:** 주담당이 자료의 공개 여부나 예정 시각을 물으면 동료가 킥오프에서 공유된 예정 시각을 참고해 답하고, 아직 보지 못한 자료라면 그렇게 말하게 한다. 이후 개인 지연 알림의 내용은 동료 답변으로 누설하지 않는다. 응답 생성에 전달되는 대화·자료 맥락과 질문 분류 경로를 확인한다.
- **확인한 문제:** 주담당이 팀 채널에서 인터뷰 요약이 왜 오지 않는지 물었을 때 이도현은 “지금 3번은 후속 모임 기능 아이디어 정리 중, 4번은 사례 조사 중, 5번은 기능 설계 초안 작성 중이에요.”라고 답했다. 인터뷰 자료의 공유 시점이나 확인 여부에 답하지 않아, 주담당은 여전히 자료 상태를 알기 어렵다.
- **결정할 점:** 해당 답변의 생성 경로와 사용 가능한 세션 맥락을 확인한 뒤, 프롬프트·컨텍스트 주입·응답 검증 중 필요한 수정 범위를 정한다.
- **상태:** 원인 조사 필요. 응답 생성 경로·컨텍스트를 조사한 뒤 계약 변경이 필요할 때만 문서에 반영한다.

## CX-11. 현재 과제 시각과 마감 시각을 같은 기준으로 표시

- **수정할 내용:** 지원자 화면에 현재 과제 시각과 마감 시각을 함께 보여 주고, 유용한 남은 시간 표시도 유지한다. 실제 기기 시각과 구분할 수 있도록 “오피스 시각” 또는 “시뮬레이션 시각”처럼 이름을 붙인다. 팀장과 동료가 말하는 자료 공유 시각도 이 시계를 기준으로 표현한다. 이 방향은 합의했다.
- **확인한 문제:** 현재는 마감까지 남은 시간만 보여 주므로 킥오프의 “01:00쯤 공유”가 과제 중 몇 시인지, 남은 시간 01:00인지 알기 어렵다. 지원자가 과제 안의 현재 시각과 마감 시각을 함께 보면 공유 약속을 같은 시계에서 확인할 수 있다. CX-09의 시간 혼동을 해결하는 기본 방향이다.
- **표시 예시:** 과제가 가상 시각 09:00에 시작해 11:00에 끝난다면 “오피스 시각 09:23 · 마감 11:00 · 1시간 37분 남음”으로 표시하고, 팀장은 “10:00쯤 공유”라고 말한다. 이는 표현 예시이며 시각 설정은 확정하지 않았다.
- **결정할 점:** 가상 시작·마감 시각과 실제 세션 길이의 대응 방식, 6분 테스트 세션의 시간 압축 방식, 채팅 타임스탬프·보드 마감 선택지·자료 공개 알림·마감 경고에 같은 시계를 적용할 범위. 예정된 지연은 지연 알림 전에 노출하지 않는다.
- **결정(F8):** 오피스 시각 09:00 시작·11:00 마감 고정, 압축 세션은 같은 비율(`09:00 + t_min × 120/L`). 상단 "오피스 시각 09:23 · 마감 11:00 · 1시간 37분 남음". 팀장·동료 발화, 자료 공개 예정, 채팅 타임스탬프, 보드 "언제까지", 마감 경고 모두 이 시계.
- **상태:** 결정 · 문서 반영 · 미구현.

## CX-12. 최종본 완료 뒤 한서윤 DM 보고와 명시적 종료

- **합의한 흐름:** 과제/최종본 탭의 **완료** 버튼을 누르면 최종본이 한서윤에게 전달된 사실을 분명히 알리고, 한서윤과의 1:1 DM으로 이동할 수 있게 안내한다. 주담당은 그 DM에서 자신의 말로 과제 완료와 결과를 직접 보고한다. 한서윤은 DM으로 짧게 확인하고 수고했다는 답장을 보낸다. 그 답장에 **종료** 버튼을 표시하고, 주담당이 눌러야 세션이 최종 종료되어 디브리핑으로 넘어간다. 최종본 전달과 주담당의 보고 메시지는 서로 다른 단계이며, 완료 버튼이 주담당의 보고 내용을 대신 작성하거나 전송하지 않는다. 제출 뒤 한서윤이 팀 채널에서 별도로 보고를 재촉하는 흐름은 없앤다.
- **확인한 문제:** Chrome 세션에서 시작 후 약 25분에 최종본을 제출하자 “최종본을 보냈어요 / 보고를 기다리는 중”이라는 시스템 메시지와 5분 보고 대기 배너가 나왔다. 이미 제출했는데 한서윤은 팀 채널에 각 파트 진행 상황을 길게 묻고 “다 됐다고 전해도 되죠?”라고 재촉했다. 주담당의 “ㅇㅇ”, “다 됐습닏” 같은 팀 채널 답변은 이도현 쪽 일반 대화로 흘러가 작업 현황 답변이 돌아왔고 세션은 보고 대기 상태에 머물렀다. 제출 완료, 보고할 대상, 보고 형식, 종료 조건이 화면에서 명확하게 연결되지 않는다.
- **현행 규칙과 변경 범위:** 현재 PRD는 제출 시 한서윤의 보고 요청을 띄우고, 팀 채널이나 팀장 DM의 메시지가 `report`로 분류되거나 5분이 지나면 세션을 종료한다. 한서윤의 확인 답장과 종료 버튼은 현행 종료 조건에 없다. 합의한 흐름은 기획상 큰 변경이므로 `docs/prd-change-proposals.md`에 기록한 뒤 팀 공유와 PRD 반영이 필요하다. 이후 공용 계약, 상태 전이, 에이전트·API·워커, 화면과 전체 흐름 테스트를 맞춰야 한다. 정직/공정한 보고의 점수는 주담당이 실제 DM에 쓴 보고를 근거로 삼으며, 최종본 전달 알림이나 한서윤의 답장이 보고를 대체하지 않는다.
- **결정할 점:** 보고하지 않은 채 머무를 때, 한서윤 답장 생성·전달이 실패할 때, 종료 버튼을 누르지 않고 이탈·재접속할 때의 복구 및 시간 제한을 정한다. 5분 자동 종료는 사용자 결정(완료 시각 기준 fallback)으로 확정했다. 01:50 보고 요청 카드는 유지하고 완료 전이면 팀 채널, 조기 완료면 한서윤 DM에서 요청하는 것이 설계 선택이다(decisions 2026-10-21). 관찰 창·평가 판정의 조정 범위는 남은 결정이다. 자동 제출 때의 안내와 종료 경로, DM 메시지가 이도현에게 잘못 라우팅되지 않도록 하는 계약도 확인한다.
- **결정(F3·F4·F5, 위 합의 흐름을 대체):** 완료 버튼 → "한서윤에게 보내기" 창(최종본 첨부, 자유 메시지 선택, "보내면 수정할 수 없어요"만) → 메시지는 한서윤 DM에 `kind=report`로 저장 → 고정 답장 "받았어요, 수고하셨어요." → 즉시 종료 → 디브리핑. 2시간 자동 완료도 메시지 없이 같은 처리. 10:50에 한서윤이 개인 DM으로 진행을 확인하며 제출했으면 보내지 않는다. 정직 근거는 제출 메시지와 그 DM 이후 한서윤 DM 메시지뿐이고 보고 시간 기준은 없다. 위 "결정할 점"(미보고 체류, 답장 실패, 종료 버튼 미클릭·재접속, 채널 분기)은 대기 단계가 사라져 해당 없음.
- **상태:** 결정 · 문서 반영 · 미구현.

## CX-13. 세로로 쌓인 화면에서 한 페이지의 핵심 내용을 보기 어려움

- **확인한 문제:** 화면 안의 내용이 긴 세로 스크롤로 이어져 현재 할 일과 진행 상태를 한눈에 파악하기 어렵다. 특히 보드는 `apps/web/components/office/board.tsx`에서 패널 폭이 680px 미만이면 할 일·진행 중·완료 3열을 세로로 쌓는다. 카드와 상세 내용까지 길어지면 상태별 현황을 비교하려고 여러 번 스크롤해야 한다. 이는 대화와 작업을 탭으로 나누는 CX-08과 별개의 정보 밀도 문제다.
- **검토할 방향:** 메인 영역에서 핵심 상태를 한 화면에 요약해 보여 주는 방법, 보드의 가로 배치 또는 상태별 개요, 긴 내용의 펼침·접힘 등을 비교한다. CX-08의 탭 전환 후 실제 사용 가능한 폭을 확인해 방식을 정한다.
- **결정할 점:** 한눈에 보여야 하는 핵심 정보, 보드와 자료·문서의 요약 범위, 좁은 화면에서의 배치와 스크롤 동작. 구체적인 UI와 적용 범위는 아직 정하지 않았다.
- **결정(F10 기본안):** 탭 전환 뒤 보드 맨 위에 상태별 개수 요약, 할 일 카드는 접힌 한 줄 기본에 펼침, 섹션 열 구성. 자료·문서는 펼침·접힘.
- **상태:** 기본안 결정 · 문서 반영 · 미구현.
