# 상대 페르소나 정의 · 외부 디텍터 (v1.0)

> 앞 문서: [00-selection-process.md](00-selection-process.md), [01-analysis-results.md](01-analysis-results.md)

## 1. 상대 페르소나 (팀장 · 동료)

지원자를 뺀 두 페르소나는 **페르소나 카드**로 정의한다(`backend/app/llm.py`의 `persona_system`). 카드는 세 겹으로 구성된다.

| 층 | 내용 | 정의 위치 |
|---|---|---|
| 정체성 | 이름, 역할, 지원자와의 관계, 말투 | `personas.py`의 `IDENTITY`, `SPEECH` |
| 입장 (무엇을) | 시나리오의 입장과 가치 축의 극(V1~V4) | `dilemmas.py`, `scenarios.py` |
| 갈등 대처 유형 (어떻게) | 행동 규칙, 양보 조건, 하지 않을 것 | `personas.py`의 `MODES` |

**유형 분류**: Thomas-Kilmann 갈등 대처 5유형을 쓴다. 주장성(1~5) × 협력성(1~5) 두 축으로 정의되는 분류다.

| 유형 | 주장 | 협력 | 핵심 행동 규칙 |
|---|---|---|---|
| 경쟁형 | 5 | 1 | 단정적으로 말하고 반대에 바로 반박한다. 근거가 두 번 나오기 전에는 양보하지 않는다 |
| 협력형 | 4 | 5 | 입장을 밝히고 상대의 진짜 걱정을 묻는다. 둘 다 살리는 안을 찾는다 |
| 타협형 | 3 | 3 | 반씩 양보하자고 빨리 제안한다 |
| 회피형 | 1 | 1 | 짧고 모호하게 답하고 결정을 미룬다. 직접 물어야 사정을 말한다 |
| 수용형 | 1 | 5 | 상대에게 맞추고, 묻기 전에는 불만을 말하지 않는다 |

**공통 규칙**:
- 유형은 '어떻게 말하는지'만 정한다. '무엇을 주장하는지'(입장)는 바꾸지 않는다.
- 규칙의 예시 문구를 그대로 반복하지 않는다.
- 서로를 '이름+님'으로 부른다.
- 평가 관련 발언과 사실 지어내기는 금지한다.

**상투 문장 후처리**: gpt-4o-mini는 프롬프트로 막아도 "필요하시면 말씀해 주세요"로 끝내는 경향이 남는다. 그래서 끝에 붙은 상투 문장을 문장 단위로 결정적으로 제거한다(`strip_boilerplate`). 발화가 상투 문장 하나뿐이면 그대로 둔다.

## 2. 무작위 균형 배정

- **조건**: (팀장 유형, 동료 유형)의 순서쌍 중 둘이 다른 20개.
- **방법**: 최소화법(minimization, Taves 1974)을 쓴다.
  - 같은 층(딜레마는 축, 카테고리 시나리오는 카테고리) 안에서 두 유형의 누적 배정 수 합이 가장 작은 조건을 고른다.
  - 동점이면 세션 ID를 시드로 한 난수로 고른다.
- **검증**: 40회 배정 시뮬레이션에서 팀장 유형은 8/8/8/8/8이었고, 동료 유형은 7~9였다. '팀장≠동료' 제약 때문에 두 축이 동시에 완전 균형일 수는 없다. 차이 ≤ 2를 테스트로 보장한다.
- **기록과 공개 범위**: 배정 조건은 세션에 저장되고 관리자 화면에만 보인다. 지원자 API에는 노출되지 않는다.
- **해석 원칙**: 상대 유형이 다르면 같은 지원자도 다르게 반응할 수 있다. 그래서 **같은 조건끼리 비교**하는 것이 원칙이다. 조건이 유형별로 고르게 쌓이면, 상대 유형에 따라 반응이 어떻게 달라지는지도 분석할 수 있다.

## 3. 외부 디텍터 (`detector-mcp`)

관찰기(OpenAI, LangGraph 내부)와 독립적으로 지원자 발화를 판정하는 MCP 서버다(`backend/mcp_servers/detector/`).

| 도구 | 종류 | 설명 |
|---|---|---|
| `describe_rubric` | 조회 | 루브릭, 규칙 사전, 사용 모델 |
| `detect_message` | 변경 | 발화 하나를 판정하고 저장 |
| `get_session_detections` | 조회 | 세션의 판정 결과 |
| `delete_session_detections` | 변경 | 재판정 전에 삭제 |

### 판정 층
1. **규칙** (`rules.py`):
   - 한국어 표현 사전 15종(질문, 정리, 구체적 약속, 모호한 약속, 인정, 통합안, 도움 요청, 반대, 주장, 비난, 근거, 변경 수용, 회피, 평가 탐색 등)을 쓴다. 모든 판정이 어떤 표현에 걸렸는지 추적할 수 있다.
   - 주장성과 협력성은 루브릭 정의대로 중립 3에서 시작해 표현에 따라 더하고 뺀다.
2. **모델**:
   - 관찰기와 **다른 계열(Gemini, 기본 `gemini-3.5-flash`)** 모델로 같은 모델끼리의 자기 일치 편향을 줄인다. temperature 0, JSON 스키마로 출력한다.
   - 근거 인용문이 원문에 없으면 해당 역량 판정을 버린다.
3. **오류 처리**:
   - 429/503 같은 일시 오류는 짧게 기다렸다 다시 시도하고, 그래도 안 되면 대체 모델(`gemini-3.5-flash-lite` → `gemini-flash-latest`)로 넘어간다.
   - 일시적이지 않은 오류(예: 모델 퇴역 404)는 바로 다음 모델로 넘어간다.
   - 모든 모델이 실패하면 규칙 판정만으로 결과를 내고 `source: rules`와 오류 내용을 기록한다.
   - 입력이 잘못되면 `ToolError`를 낸다.

### 백엔드 연동
- 매 턴이 끝나면 지원자 발화를 백그라운드로 판정한다. 세션 락으로 턴 저장과 직렬화해 변경 분실을 막는다.
- 리포트를 만들 때 빠진 판정을 채운다(backfill).
- 리포트 생성은 세션 락 밖에서 하도록 바꿔서 교착을 막았다.
- `DETECTOR_MCP_URL`이 없으면 디텍터를 끄고, 화면에 '미연결'로 표시한다.

### 산출물 (관리자 화면)
- **지원자 성향 추정**: 주장성·협력성 평균과 가장 가까운 유형. 발화별 점과 배정된 상대 유형 위치를 같은 평면에 그린다. 성향 기술일 뿐 점수가 아니다.
- **관찰기 ↔ 디텍터 일치도**: 발화×역량 단위의 Cohen's κ(역량별, 전체)와 일치율.
- **엇갈린 판정 목록**: 관찰기와 디텍터가 다르게 본 항목. 사람이 검토하도록 해당 대화로 이동하는 링크를 준다.
- **규칙 vs 모델 평균 차**: 두 판정 층이 서로 얼마나 다른지 보여 주는 내부 점검 지표.

## 4. 실측 (실제 LLM, 같은 대본의 지원자 4세션)

| 조건 (팀장 · 동료) | 지원자 추정 (주장 / 협력) | 전체 κ | 규칙-모델 평균 차 |
|---|---|---|---|
| 경쟁형 · 타협형 | 4.00 / 4.71 → 협력형 | .34 | (보정 전) |
| 수용형 · 경쟁형 | 4.14 / 4.57 → 협력형 | .43 | (보정 전) |
| 협력형 · 수용형 | 4.14 / 5.00 → 협력형 | .44 | (보정 전) |
| 타협형 · 협력형 | 3.86 / 4.57 → 협력형 | .34 | 0.43 / 0.71 |

- **추정 안정성**: 같은 지원자 대본은 상대 유형이 달라도 모두 '협력형'으로 추정됐다. 상대 조건에 대해 추정이 안정적이라는 신호다.
- **규칙 보정**: 보정 전 규칙 판정은 체계적으로 낮았다(주장 2.1 대 모델 4.1). 기준점(중립 3)과 표현 사전을 고친 뒤 평균 차가 1.93 / 1.79 → 0.64 / 0.79로 줄었다. 다만 **원인을 진단한 같은 발화로 잰 표본 내 수치**라서, 새로운 발화로 다시 검증해야 한다.
- **일치도 수준**: κ .34~.44는 '보통 이하~중간' 수준이다. 역량별로는 C03(약속·공유)이 .70 안팎으로 가장 높았고, C02(조율)와 C05(변화 대응)는 낮거나 0이었다. 이 두 역량은 정의를 더 다듬거나 사람의 코딩을 기준으로 다시 봐야 한다.

## 5. 한계와 다음 단계
- 관찰 대상(지원자)이 대본 하나뿐이라, 디텍터가 서로 다른 지원자를 얼마나 잘 구분하는지는 아직 보지 못했다. 다음 단계는 사람 평가자 2인의 코딩을 기준으로 관찰기와 디텍터 각각의 κ를 재는 것이다.
- 페르소나가 유형 규칙을 얼마나 지키는지(조작 점검)도 별도로 재야 한다. 예를 들어 페르소나 발화를 디텍터로 판정해서, 경쟁형이 실제로 높은 주장성으로 판정되는지 확인한다.
- 상대 유형별 효과 분석은 조건당 세션이 충분히 쌓인 뒤 가능하다(20조건).
