# 리뷰 브리프: 사용자 관점 리뷰 2종 (Claude, 개발 전)

두 에이전트가 각각 한 관점으로 읽는다. 둘 다 읽기 전용, 결과는 Markdown 파일로 저장하고 마지막 응답은 경로 한 줄. 한국어. 파일:줄 근거보다 "사용자가 겪는 장면" 단위로 쓴다.

공통으로 읽는 것: PRD.md → docs/frontend/design-direction.md → docs/frontend/design.md → docs/common/scenario-model.md → docs/common/rubric.md → (관리자 관점만) docs/common/contracts.md의 리포트 JSON.

## A. 면접 참가자(지원자) 관점 → docs/handoff/reviews/review-candidate-view.md
당신은 리모트 스타트업에 지원해 초대 링크를 받은 지원자다. 안내·동의 → 대기 → 2시간 세션(킥오프, 분업, 도움 요청, 자료 지연, 방향 변경, 리뷰·반대 의견, 제출·보고) → 디브리핑을 장면별로 머릿속에서 겪어 보고 적는다.
- 각 장면에서 "무엇을 해야 하는지"가 화면과 메시지로 분명한가. 막히는 지점(어디에 쓰지, 누구에게 보내지, 최종본은 어떻게 만들지)은 어디인가.
- 평가받는다는 느낌이 드는 요소, 연출이 티 나는 순간, 불쾌하거나 억지스러운 상황(특히 보고 압박, 자료 지연 알림, 동료의 반대 의견)이 있는가.
- 2시간 안에 할 수 있는 양인가. 문서 5개 파트 + 최종본 통합 + 왕복 피드백이 과한가.
- 접속 끊김·재접속·조기 제출·시간 만료 같은 예외에서 당황할 지점.
- AI 어시스턴트와 동료 AI의 역할이 헷갈리지 않는가. 동료가 AI임을 아는 상태에서 협업 동기가 생기는가.
- 디브리핑에서 받는 설명이 납득되는가. 점수를 못 보는 것에 대한 불만은 어떻게 다룰지.
- 빠진 기능·맥락 목록(있어야 자연스러운데 없는 것)과 지워도 되는 것.

## B. 채용 담당자(기업 관리자) 관점 → docs/handoff/reviews/review-admin-view.md
당신은 10~30명 리모트 스타트업의 채용 담당자다. 가입 → 채용 건 생성(미션·요소 선택) → 지원자 초대 → 진행 확인 → 리포트 검토·조정 → 면접 활용까지 겪어 보고 적는다.
- 요소 5개의 이름·뜻·"이렇게 봅니다"만 보고 무엇을 고를지 판단할 수 있는가. 상황을 숨기는 것이 선택에 방해가 되는가.
- 리포트(산출물 최종본·출처, 요소별 카드 소섹션·항목·근거, 담당자 조정, AI 활용)가 면접에서 바로 쓸 수 있는 형태인가. 부족한 정보, 과한 정보.
- "같은 채용 건 안에서만 비교"와 "기록 없음은 분모 제외" 규칙을 담당자가 오해 없이 쓸 수 있는가.
- 지원자 간 비교 화면, 초대 관리, 재응시, 보관 90일, 실패 세션 처리에서 빠진 맥락.
- 법·윤리·신뢰: "AI가 관찰하고 사람이 판단" 구조가 담당자에게 설득되는가, 지원자에게 어떻게 설명할지 안내가 있는가.
- 빠진 기능·맥락 목록과 MVP에서 지워도 되는 것.
