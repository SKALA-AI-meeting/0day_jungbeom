# 지원자 실사용 점검 기록

지원자 입장에서 화면과 흐름을 직접 확인하며 발견한 문제를 한 항목씩 쌓는다. 이 문서는 수정 논의를 위한 기록이며, `PRD.md`와 `docs/`의 설계 정본은 아직 아래 방향으로 변경하지 않았다. 구현 범위와 계약을 확정할 때 정본에 반영한다.

## CX-01. 팀 채널과 이도현 DM의 시작 대화 중복

- **현재 현상·근거:** Chrome에서 확인한 킥오프 화면에서 이도현의 DM 인사와 팀 채널 답변이 모두 주담당의 분업 결정을 따르겠다는 비슷한 내용이다. 분업 요청까지 DM으로 오면 어느 대화창에서 일을 진행해야 하는지 모호해진다.
- **합의 방향:** 팀 채널을 분업·공동 결정·문서 공유의 기본 공간으로 사용한다. DM은 개인적인 도움 요청과 별도 확인에 사용한다. 시작 시 중복되는 이도현 DM 인사를 없애고 분업 요청을 팀 채널로 옮긴다.
- **미정·영향:** 메시지 발생 시점과 채널별 문구, 기존 DM 기반 분업 흐름 및 관찰 규칙의 변경 범위를 구현 전에 확인한다.
- **상태:** 기록·미구현.

## CX-02. 미리 채워진 보드가 주담당의 분해·위임 경험을 약화

- **현재 현상·근거:** 시작 보드에 할 일 카드 5개가 이미 만들어져 있다. 담당은 비어 있어도 주담당이 일을 직접 나누고 맡기는 경험이 약하다.
- **합의 방향:** 최종본의 5개 섹션 템플릿은 유지하고 보드는 빈 상태에서 시작한다. 지원자가 할 일을 만들고 섹션에 연결해 담당을 지정한 뒤 **분업안 공유**로 팀 채널에 전달한다. 이도현은 공유된 자기 일을 시작한다.
- **추가 제안:** 빈 보드의 길잡이로 자료 탭에 '기본 작업 흐름 예시'(문제·대상 → 인터뷰 근거 → 핵심 기능 → 사례 → 지표·일정)를 보여 준다. 현재 자료 탭에는 회사·서비스 소개, 지표 현황, 잠긴 인터뷰 요약, 운영 정책, 지난주 회의록만 있다. 흐름 **예시**와 담당 **필수 제약**은 구분하며, 이 제안은 아직 확정하지 않았다.
- **미정·영향:** 할 일 생성·수정 규칙, 섹션 연결과 담당 지정의 필수 조건, 공유 후 재분업 처리, 미공유 시 진행 방식, 평가·이벤트·API 계약은 미정이다. 기존의 '5개 카드 담당을 모두 채우면 자동 확정' 규칙을 바꾸는 큰 PRD 변경이므로 별도 변경 제안과 팀 공유가 필요하다. CX-04와 함께 초기 담당과 필수 제약을 어떻게 보여 줄지 재논의한다.
- **상태:** 방향 합의·미구현. PRD 변경 대기.

## CX-03. 한서윤 킥오프에 마감 보고 요청 문구가 섞임

- **현재 현상·근거:** Chrome에서 확인한 한서윤의 첫 공지에 마감 때 나와야 할 “다 됐다고 전해도 되죠?”가 포함됐다. 프롬프트는 이 문구를 보고 요청 카드에서만 허용하지만 실제 LLM 생성 결과가 어겼다.
- **합의 방향:** 킥오프 공지를 자연스럽고 간결하게 정리한다. 보고 요청 문구는 해당 카드에서만 나오도록 결정적 검증을 두고, 위반 시 재생성하거나 안전한 문구로 교체한다.
- **미정·영향:** 금지 문구의 검사 범위와 재생성·안전 문구 중 적용 순서, 유사 표현 처리 기준은 구현 전에 정한다. 프롬프트와 메시지 검증 경로에 영향이 있다.
- **상태:** 기록·미구현.

## CX-04. 담당 필수 조건을 마지막 카드에서야 알게 됨

- **현재 현상·근거:** Chrome 보드에서 2번 '사용자 인터뷰에서 찾은 근거'를 이도현, 3번 '핵심 기능 제안'을 주담당, 4·5번을 이도현으로 두고 1번 담당을 정해 5/5로 확정하려 할 때, 보드 상세에 “2번 인터뷰 근거는 인터뷰를 직접 보실 주담당님이 맡아야 3번까지 흐름이 이어져요.”라는 오류가 나타났다. `services/api/app/services/board.py`의 `candidate_update`는 5개 담당이 모두 채워졌을 때 `check_division`을 실행한다. 현행 PRD 6.2는 2번 주담당, 3번 이도현 또는 공동, 4·5번 중 하나 이상 이도현 단독을 최소 조건으로 둔다. 자유롭게 맡길 수 있는 듯한 화면에서 필수 조건을 미리 알 수 없어 마지막에야 거절된다.
- **논의 중인 방향:** 필수 담당이 있다면 처음부터 보드에 담겨 있는 편이 낫다는 사용자 제안이 있다. 가능한 정리안은 고정 섹션의 담당·제약을 시작부터 공개하고 주담당이 별도 할 일을 만드는 방식, 또는 필수 조건을 없애고 후속 카드를 분업에 맞춰 적응시키는 방식이다. 어느 쪽도 확정하지 않았다.
- **미정·영향:** CX-02의 빈 보드 합의와 초기 담당·제약 공개 방식을 함께 재검토해야 한다. 필수 조건을 제거하면 시나리오 카드와 평가 근거까지 바뀌는 큰 변경이다.
- **상태:** 관찰·방향 논의 중.

## CX-05. 회사 자료가 Markdown 원문으로 보여 읽기 어려움

- **현재 현상·근거:** Chrome의 자료 탭에서 지표 현황 표의 `|`·`---`, 지난주 회의록의 `#`·`##`·`-`·`**`가 서식 대신 문자로 보인다. `apps/web/components/office/library.tsx`의 자료 본문은 `article` 안에 `content`를 그대로 출력하고 `whitespace-pre-wrap`만 적용한다.
- **개선 방향:** 회사 자료를 제목·목록·표·강조가 구분되는 읽기 전용 뷰어로 표시한다. 긴 자료도 읽기 쉽도록 본문 폭과 자료 영역의 스크롤을 정리한다.
- **미정·영향:** Markdown 렌더링 방식과 표의 좁은 화면 처리 방식은 구현 시 정한다. 자료 원문과 공개 시점은 유지하며 자료 화면 컴포넌트에 영향이 있다.
- **상태:** 사용자 지적·개선 필요 확정·미구현.

## CX-06. 자료와 내 문서 사이를 계속 왕복해야 함

- **현재 현상·근거:** Chrome에서 자료와 내 문서가 오른쪽의 같은 탭 영역에 있다. 회사 자료를 읽으며 기획안 본문을 쓰려면 두 탭을 계속 왕복해야 한다.
- **논의 중인 방향:** CX-08의 메인 탭 구조에서 자료를 참고하며 내 문서를 작성하는 흐름을 다시 검토한다. 자료와 편집기를 함께 표시하는 방식은 확정하지 않았다.
- **미정·영향:** 자료와 내 문서 간 이동·참조 방식, 작은 화면에서의 동작과 기존 문서 열기 흐름에 미칠 영향은 미정이다.
- **상태:** 관찰·해결 방식 미정.

## CX-07. 지난주 회의록과 이번 과제의 마감이 달라 혼동할 수 있음

- **현재 현상·근거:** 자료 탭의 지난주 프로덕트 회의록은 기획안 초안을 2주 안에 만들고 다음 분기 로드맵에 넣는다고 적는다. 이번 한서윤의 킥오프 요청은 세션 끝인 2시간 뒤 기획안 초안을 받겠다는 내용이다. 주담당이 이전 회의의 일정과 현재 요청 중 무엇을 따라야 하는지 잠시 혼동할 수 있다.
- **논의 중인 방향:** 회의록이 이전 계획이고 이번 요청이 별도의 압축 과제임을 짧게 밝히거나, 회의록의 일정 문구를 이번 과제 맥락에 맞게 정리한다.
- **미정·영향:** 설명을 어느 화면·자료에 둘지, 시나리오 자료 문구를 변경할지는 미정이다. 일정 변경 카드와의 연결도 확인해야 한다.
- **상태:** 관찰·해결 방식 미정.

## CX-08. 대화와 작업 영역이 한 화면에 함께 보여 공간을 나눠 씀

- **현재 현상·근거:** 현재 화면은 왼쪽 채널 목록, 가운데 채팅, 오른쪽 내 문서·보드·자료·어시스턴트를 동시에 보여 준다. 사용자는 채팅하면서 작업을 하지는 않으므로 대화와 작업을 한 화면에 계속 띄워 둘 필요가 없다고 지적했다.
- **사용자 제안·레이아웃 방향 합의:** 오른쪽 작업 영역을 메인 화면의 탭으로 옮겨 대화와 작업을 전환한다. 채널 목록과 남은 시간은 유지하고, 메인 영역에서 대화·내 문서·보드·자료·어시스턴트로 이동하는 구성을 제안한다.
- **상세 UX 제안:** 작업 탭에 있을 때 새 메시지 알림·배지를 보여 주고 해당 대화로 돌아가는 경로를 둔다. 탭의 정확한 구성과 전환 방식은 아직 확정하지 않았다.
- **미정·영향:** 채널별 대화 전환, 작업 상태 보존, 알림 방식, 작은 화면 배치와 CX-06의 자료 참조 흐름을 함께 검토해야 한다. 화면 구조 변경 범위는 구현 전에 정한다.
- **상태:** 사용자 제안·레이아웃 방향 합의·상세 미정·미구현.
